# Required Permissions for CDK Integration Tests

This document provides an overview of the IAM permissions required to run CDK integration tests.

## About This Document

This document serves as documentation for the permissions used during CDK integration test execution. The actual permission data is automatically generated by the permission snapshot testing feature.

## How This Document is Generated

When integration tests are run with permission tracking enabled, each test generates a permission snapshot file (`.permissions.snapshot.json`). These individual snapshots can be aggregated into a comprehensive permissions document using the `@aws-cdk/integ-permissions-tracker` package.

### Generating the Aggregate Permissions Document

To generate or update the aggregate permissions document:

```bash
# Run integration tests with permission tracking
CDK_INTEG_PERMISSIONS_SNAPSHOT=true yarn integ --directory packages/@aws-cdk

# The aggregate will be generated at:
# .permissions/permissions-aggregate.json
```

### Programmatic Access

```typescript
import {
  aggregateSnapshots,
  formatAggregateAsMarkdown,
  writeAggregateSnapshot,
  getDefaultAggregateSnapshotPath,
} from '@aws-cdk/integ-permissions-tracker';

// Aggregate multiple test snapshots
const aggregate = aggregateSnapshots(snapshots);

// Write as JSON
writeAggregateSnapshot(aggregate, getDefaultAggregateSnapshotPath(projectRoot));

// Format as markdown documentation
const markdown = formatAggregateAsMarkdown(aggregate);
```

## Understanding the Permissions

### Permission Snapshot Format

Each integration test generates a snapshot containing:

- **Roles**: IAM roles that are assumed during test execution (e.g., deployment roles, execution roles)
- **Actions**: AWS API actions that are called, organized by service

Example snapshot:

```json
{
  "version": "1.0",
  "roles": [
    "arn:aws:iam::123456789012:role/cdk-hnb659fds-deploy-role-123456789012-us-east-1"
  ],
  "actions": {
    "cloudformation": ["CreateStack", "DeleteStack", "DescribeStacks"],
    "s3": ["GetObject", "PutObject"],
    "sts": ["AssumeRole"]
  }
}
```

### Common Permission Categories

#### CDK Deployment Permissions

These permissions are required by the CDK to deploy CloudFormation stacks:

- `cloudformation:*` - Stack operations
- `s3:*` on CDK bootstrap bucket - Asset storage
- `sts:AssumeRole` - Role assumption for deployment

#### Service-Specific Permissions

Each CDK construct may require additional permissions based on the AWS resources it creates. For example:

- Lambda constructs: `lambda:CreateFunction`, `lambda:DeleteFunction`
- S3 constructs: `s3:CreateBucket`, `s3:PutBucketPolicy`
- DynamoDB constructs: `dynamodb:CreateTable`, `dynamodb:DeleteTable`

### Aggregate Permissions Structure

The aggregate document combines all test permissions:

```json
{
  "version": "1.0",
  "generatedAt": "2024-01-15T10:30:00.000Z",
  "testCount": 150,
  "roles": ["arn:aws:iam::..."],
  "permissions": {
    "s3": [
      { "action": "GetObject", "tests": ["integ.bucket", "integ.lambda"] },
      { "action": "PutObject", "tests": ["integ.bucket"] }
    ]
  }
}
```

## Interpreting Permission Changes

When a permission snapshot changes, it indicates that:

1. **New permissions are required**: A test now needs additional AWS API access
2. **Permissions were removed**: A test no longer needs certain AWS API access
3. **Roles changed**: Different IAM roles are being assumed

### Security Considerations

Permission changes should be carefully reviewed:

- **Added permissions**: Verify they are necessary for the new functionality
- **Removed permissions**: Confirm the functionality still works without them
- **Role changes**: Ensure the correct roles are being used

### Updating Snapshots

When permission changes are intentional:

```bash
# Update a single test's snapshot
yarn integ test/aws-lambda/test/integ.lambda.js --update-permissions-snapshot

# Update all snapshots in a module
yarn integ --directory test/aws-lambda/test --update-permissions-snapshot
```

## CI/CD Integration

### GitHub Actions

Permission changes in pull requests will be reported in the CI output:

```
::error file=integ.lambda.permissions.snapshot.json::Permission snapshot changed (+2 actions, -1 actions)
::warning::1 permission snapshot(s) need to be updated. Run with --update-permissions-snapshot
```

### Reviewing Permission Changes in PRs

When reviewing a pull request with permission changes:

1. Check the diff output in CI logs
2. Verify changes align with the PR's intended functionality
3. Ensure no unintended permission escalations
